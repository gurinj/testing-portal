# M3 – Service desk features: fix the errors, run comparison, create email

**Status:** in progress · started 2026-11-24 · green light 2026-11-24
**Version:** 0.4.0-m3
**Source of the design:** prototype v2 (`claude/testing-portal-prototype-v2.html` in the project: screens "Proposed changes", runs strip, "Email for the customer", printable report) and the plan (`claude/testing-portal-static-app-plan.md`, sections 5 and 11).

## 1. Decisions for M3 (2026-11-24)

- Country specifications come after M3 is released; until then only the generic rules of the catalogue (as in M2). M3 adds no country rules.
- The user tests M3 at work, including the bank's files; one round of corrections (M3.1) covers M2 and M3 findings and the six open M2 decisions. M4 (first release) can follow with the generic rules only.
- Fixes come from `config/fixes.json`, drafted by us, reviewed by the user.
- **Pre-selection:** changes calculated from the file that do not change what the payment does are ticked (counts, control sums, spaces, control characters, transliteration). Changes that change what the payment does (execution date, charge bearer, shortened names, new ids), sample values, choices and entered values are proposed but not ticked. "Select all" ticks everything.
- **Only the fixed values change.** A fix edits the file text at the exact place of the value; every other character of the file stays as the customer sent it (line breaks, indentation, comments, namespace prefixes, encoding declaration, BOM).
- Structural XSD errors (2.1–2.5), wrong IBANs, BICs and amounts are never guessed. For IBANs and BICs the fix screen offers an empty field where the user can type the correct value, checked before it is applied.
- Run comparison: findings matched by check (id and part) and place (EndToEndId and PmtInfId, else the path), so it also works on a new version of the file. Kept for the browser session only.
- Email: English only, signed "Payments Service Desk", text in `config/templates/email.en.json`. "To" is empty (the tool does not know the customer's address). Copy (main way) and "Open in email app" (mailto with subject and text; attachments are added by hand; some mail programs cut long texts).
- Nothing is stored and nothing is sent: runs, changes and email text last until the page is reloaded.

## 3. Fixes

### 3.1 `config/fixes.json`

```json
{
  "_about": "…",
  "fixes": {
    "4.4":       { "action": "ctrlSumFile", "field": "Control sum (group header)" },
    "5.4-spaces":{ "action": "trim", "field": "Text with spaces at the start or end" },
    "4.10":      { "action": "nextBusinessDay", "field": "Requested execution date", "changesPayment": true },
    "7.19":      { "action": "choice", "field": "Charge bearer", "options": ["SHAR", "DEBT", "CRED"], "default": "SHAR" },
    "4.28":      { "action": "insertSample", "field": "Creditor name", "element": "Cdtr/Nm", "sample": "Sample Creditor Name", "check": "text70" },
    "5.6-cdtr":  { "action": "entry", "field": "Creditor IBAN", "check": "iban" },
    "2.2":       { "manual": "Add the missing element in the system that creates the file." }
  }
}
```

- Key: check id, or id and part (`5.6-cdtr`); a part key wins over the id key. A check without an entry is manual.
- `action`: name of a function in `TP.fix.actions` (section 3.3). `field`: the label on the fix screen and in the email.
- `kind` follows from the action: `calculated` (value from the file), `sample` (a marked placeholder for missing data), `choice` (one of `options`, default `default`), `entry` (no value proposed, the user types one), `manual` (no change).
- `changesPayment: true`: a calculated change that changes what the payment does; not ticked.
- `check`: validator for samples, choices and entries (`TP.fix.checks`): `iban`, `bic`, `text35`, `text70`, `text140`, `code4`, `date`, `id35` …
- Settings may switch a fix off later (`settings.fixes."4.4": false`), not needed now.

### 3.2 Proposals and changes

`TP.fix.propose(result, text, ctx)` → `{ proposals: [Proposal], manual: [{ group, reason }] }`

```
Proposal = { id, group: <report group id>, rule, part, title, field, kind, changesPayment, sel, options, check,
             rows: [Row] }                     // one row per place of the finding group
Row      = { where, block, tx, e2e, op, path, attr?, insert?, old, next, val, error }
             op: 'text' (replace the text of a leaf element) | 'attr' (replace an attribute value)
               | 'insert' (insert a new element) | 'remove' (remove an element)
             path: element path as in the findings ("/Document[1]/CstmrCdtTrfInitn[1]/PmtInf[2]/…")
             insert: { parent: path, name: 'Nm', after: ['…names that come before it in the XSD…'] }
             old: current value (null if missing), next: proposed value, val: value to apply (edited by the user)
```

- One proposal per report group (a finding with 200 places is one proposal with 200 rows). For samples, choices and entries the value is the same for all rows of a proposal (one input); per-row editing is not needed in M3.
- Rows the action cannot compute are left out; if none is left, the group is listed as manual with the action's reason.
- `sel` from section 1; the user changes it.

`TP.fix.apply(text, proposals)` → `{ text, applied: [AppliedGroup], skipped: [{ rule, where, reason }] }`

```
AppliedGroup = { rule, part, title, field, kind, rows: [{ where, block, tx, e2e, old, next }] }
```

- Only selected proposals, only rows without `error`.
- Positions from `TP.fix.locate(text, paths)` (one saxes pass): for each path the start and end of the element, the end of its start tag, the start of its end tag, self-closing or not, the indentation of its line, and its children's names in order.
- Text values are written escaped (`&`, `<`, `>`; `"` in attributes); the old raw text, with its entities, is replaced as a whole.
- Inserted elements get the indentation and line break style of a sibling (or the parent's indentation plus two spaces) and go after the last existing child named in `after`, else as the first child.
- Edits are applied from the end of the file to the start, so positions stay valid. Two edits on overlapping ranges: the first in document order is applied, the other is skipped with a reason.
- The corrected file is UTF-8, with the original BOM if there was one, named `<name>_corrected.xml` (`_corrected2` … for later rounds).

### 3.3 Actions

```
TP.fix.actions[name] = {
  kind: 'calculated' | 'sample' | 'choice' | 'entry',
  needs?(ctx, group, def) → { paths: [element paths whose values are needed], children: [paths whose children are needed] },
  rows(ctx, group, def)   → [Row] | { rows: [Row], reason }      // reason: why no row could be made (shown as manual)
}
ctx = { result, text, settings, country, countryConfig, F: TP.functions, node(path) → located element (js/fix/locate.js) or null }
```

- `propose` collects the `needs` of all actions and reads the file once (`TP.fix.locate`); `ctx.node` answers only for those paths.
- Helpers in `js/fix/propose.js`: `TP.fix.row(item, fields)` (copies where, block, tx, e2e of a finding item), `under(path, 'Cdtr/Nm')`, `candidates(path, rel)` (the path and its ancestors), `whereOfPath(path)`, `parentOf`, `nameOf`.
- Generic actions in `js/fix/actions/generic.js`: `choice`, `entry`, `sample`, `insertSample`, `trim`, with `def.element` (relative to the finding's element) and `def.up` (the element may be on the transaction or on its block; one row per element).
- Actions for particular checks: one file per kind of check under `js/fix/actions/`, each with tests. They use the values the report already has (`item.actual`, `result.blocks` with the transactions' amounts and currencies) and `ctx.node` for other elements. `TP.context` is set (settings, country) so the functions of the rules can be used (`F.translit`, `F.tpNonBusinessDay`, `F.tpCcyDecimals` …).

### 3.4 After applying

The corrected text runs through the same pipeline (same country, same settings) as a new run of the session (`source: 'fix'`, `parent`: the run it came from). The report shows the runs strip, the changes applied and the sample values still to replace.

## 4. Session: runs

```
state.session = { runs: [Run], current: <n> }
Run = { n, fileName, label, at, country, version, status, counts: { E, W, I }, incomplete, source: 'upload' | 'fix',
        parent: <n> | null, changes: [AppliedGroup], text (for the last 3 runs), result (for the last 3 runs) }
```

- A new upload starts a new chain unless it is a new version of the same file (same country, the same file name without `_v2`, `_corrected` …, and where both say it the same debtor account or initiating party; review R4), then its `parent` is the latest run of that chain.
- Only the last 3 results are kept in full (memory); older runs keep their counts and the comparison keys (`run.keys = TP.compare.keysOfRun(run)`, set when the result is dropped).

## 5. Comparison (`js/compare/compare.js`)

`TP.compare.keysOf(result)` → `Map<key, { group, item }>`; `TP.compare.runs(a, b)` (two results or two key maps) → `{ resolved: [Group], open: [Group], new: [Group], counts: { resolved, open, new } }` with `Group = { rule, part, title, severity, level, items: [{ where, e2e, line }] }`.

- Key: `rule-part` + place. Place: file level → `file`; block level → `B:<PmtInfId>` (else `B#<n>`); transaction level → `T:<PmtInfId>/<EndToEndId>` (else `T#<block>/#<tx>`, so an EndToEndId "7" is not taken for a position); with a running number when the same key repeats (duplicate ids); XSD findings add the element name and the message template.
- A finding whose severity changed counts as still open.

## 6. Email (`js/email/build.js`, `config/templates/email.en.json`)

`TP.email.build(session, run, ctx)` → `{ to: '', subject, body, attachments: [{ kind: 'report' | 'xml', name }] }`

Cases, each a subject and a text in the template file, with placeholders (`{file}`, `{country}`, `{errors}`, `{warnings}`, `{hints}`, `{changes}`, `{samples}` (list), `{findings}` (list) …) and plural forms:

| Case | When |
|---|---|
| `unreadable` | stopped at stage 0 |
| `unsupported` | stopped at stage 1 |
| `rejected` | RJCT, no changes applied |
| `fixed` | changes applied (from the first run of the chain to the current run): what was found, the corrected copy for reference only, sample values to replace, change the system that creates the files |
| `warnings` | ACWC, no changes |
| `passed` | ACTC, no changes |
| `incomplete` | added sentence when some checks could not run |

Every text that says the file passed ends with the note that a passed technical check does not guarantee execution (account, funds, entitlements and sanctions are not checked). Signature "Kind regards / Payments Service Desk".

## 10. Decisions while building

(Recorded as they are taken.)

1. **Corrected file name.** `<name>_corrected.xml` for the first fix round of a file, then `_corrected2`, `_corrected3` …; the name comes from the first run of the chain, so a renamed file keeps the customer's name.
2. **Pre-selection.** `sel = kind === 'calculated' && !changesPayment`; everything else is proposed but not ticked (spec §1). A value the user types into a sample field turns it into an *entered* value (tag and report).
3. **Charge bearer 7.19 at block level.** The finding is on each transaction, the element is on the block (`PmtInf/ChrgBr`). The fix walks up (`"up": true`), and one row per block is shown; the place is the block.
4. **Overlapping changes.** When two changes touch the same text, the first in document order is made and the other is listed as *could not be made* in the report (never a guess).
5. **Inserted elements follow the file.** Indentation and line endings of the neighbours are used; children written on one line stay on one line.
6. **Long lines in the before/after view** are shown from shortly before the change, with "…" in front, so a change in a one-line file is visible.
7. **Exports.** The printable report gets the runs, the original result (findings of run 1 while it is still kept; the session keeps full results for the last 3 runs), the sample values, the changes and the remaining findings. The CSV gets a *Run* column first. The summary gets `run` and `runs` (number, source, status, counts, number of changes) only when there is more than one run; still no file name and no values.
8. **Technical check.** A tenth built-in check runs a whole fix round on a made-up UA cross-border file (charge bearer, missing creditor name, trailing space) and expects the corrected file to be byte-for-byte the clean file.
9. **Changes count from the latest upload.** `TP.session.changesOf` and `correctedName` look at the runs since the latest upload of the chain (`TP.session.segment`). When the customer sends a new version (`salaries_v2.xml`) after a fix, the report and the email treat it as the customer's own file: no "changes made", no corrected copy, and a later fix of it is named `salaries_v2_corrected.xml`. The chain itself (runs strip, comparison) still goes back to the first upload.
10. **Comparison (c1).** Counted per place; the strip counts findings per check like the report. A check gone everywhere is *resolved*; fixed at some places only, it is resolved there and still open elsewhere. Findings of checks that did not run in the other run (it stopped, or the rule checks failed) go into a fourth list, *not compared*, never into resolved or new. Matching is by key first, then by position only where the id at that position was changed in a fix. Known limit: a payment without EndToEndId is known by its position only.
11. **Email (e1).** Lists show errors and warnings (hints only in the passed case), at most 10 lines plus "and N more". Messages of findings and old/new values of changes are never used (they quote values: amounts, IBANs); stage 0 and 1 messages are, for the "Reason:" line. Changes are listed by field and place; sample values have their own list with the value. No confirm dialogs (blocked in sandboxed frames): Reset offers Undo.
12. **Fixes per check (f1).** 158 entries in `config/fixes.json`, every check id written out (manual ones with their reason): 23 calculated and ticked, 32 calculated not ticked (they change the payment), 1 choice (7.19), 7 samples, 13 entries, 82 manual. Details in the file's `_about` and per entry `note`.
13. **Characters (5.1), to confirm.** Letters get their plain form; `&` → `+`, `_` → `-`, `@` → `(at)`, `€` → `EUR`, quotes → `'`, brackets → `( )`; anything else a space. Not ticked. No EPC conversion table was found to confirm this map.
14. **One change per text.** When one text has several of 5.1, 5.2, 5.3 and 5.4-spaces, one proposal (the first of 5.1, 5.3, 5.4-spaces, 5.2) changes it and fixes all; the others are listed as manual with "Changed together with …".
15. **Dates.** 2.10 converts only forms with one meaning (`25.11.2026`, `2026/11/25`, `20261125`); `11/12/2026` stays manual. 4.10/10.1: today, or the next business day (TARGET days for EUR); SEPA Instant: today.
16. **Charge bearer on a mixed block** is not changed if a transaction of the block would then break; the finding stays manual with the reason.
17. **One typed value for all places.** An entry is offered only when all places have the same old value (the same wrong IBAN in three transactions); otherwise manual.
18. **Not offered (yet):** 4.26, 4.31, 7.9 and 7.17 (they would need a nested insert of a typed value).
19. **Independent review (17 points), fixed:**
    - R1 rows of one change (join remittance lines, date instead of date and time) carry a `unit`: made all or none, so no text is lost when another change touches one of them.
    - R2 inserted elements get the parent's namespace prefix.
    - R3 unique ids (9.1–9.3) in linear time (10,000 copies of one EndToEndId: 0.6 s instead of 24 s).
    - R4 a new upload continues a chain only with the same country, file name stem and debtor (MsgId alone is not enough), so another customer's file name never shows in a report.
    - R5 a value with an XML comment inside is never rewritten (manual, with the reason).
    - R6 typed BICs are checked against the schema's pattern of the file's version; typed text against the payment's character set.
    - R7 Back, Forward and reload on `#fix`, `#compare` or `#email` without their state: the fix screen is rebuilt for the current run, otherwise the report (or the start) with the address to match.
    - R8 a fix is validated again with the settings of the run it corrects.
    - R9 the fix screen keeps its end above the sticky bar (padding from the bar's height).
    - R10 unticked rows grey instead of faded (contrast); input errors with `aria-invalid`, `aria-describedby` and a polite live region.
    - R11 two edits that only add text at the same place (two values for one empty element, two inserts into one parent) overlap: the second waits for the next round.
    - R12 LIMITS: duplicate or NOTPROVIDED EndToEndIds in the comparison (InstrId as a second key is left for later).
    - R13 the corrected-file download says so where XML cannot be downloaded (artifact mode, not delivered).
    - R15 the disclosure marker of "Show all places" is hidden.
    - R16 a calculated change of an id (MsgId, PmtInfId, InstrId, EndToEndId, e.g. 5.2 "Müller-01" → "Muller-01") is proposed, not ticked, and marked "Changes the payment".
    - R17 corrected names: an uploaded `x_corrected.xml` gives `x_corrected2.xml`; fixing the original again never reuses an earlier corrected name.
